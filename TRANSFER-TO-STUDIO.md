# Transfer this project into Roblox Studio with Rojo

## One-time setup

1. Install Roblox Studio and create a **new private development experience**. Publish it once so it has a place/universe ID.
2. Install the Rojo CLI using the current instructions at [rojo.space](https://rojo.space/). Install the Rojo Studio plugin from the Rojo documentation/plugin link. Start Studio and open the development place.
3. In Studio, open **Plugins → Rojo**. Keep Studio open while the local Rojo server runs.
4. Install a Luau editor (VS Code is common) and open this project folder, the folder containing `default.project.json`.
5. Add ProfileStore from its upstream repository as a ModuleScript at `src/ServerScriptService/Packages/ProfileStore.lua`. Preserve its license and pin the version/commit you use. This project expects the current API: `ProfileStore.New`, `StartSessionAsync`, `Reconcile`, `OnSessionEnd`, and `EndSession`.

## Connect and sync source into Studio

1. Open a PowerShell terminal in this project folder.
2. Run `rojo serve default.project.json` and leave the terminal running.
3. In Studio's Rojo plugin, connect to the local server (usually `localhost:34872`). The Rojo tree appears in Explorer under ReplicatedStorage, ServerScriptService, and StarterPlayerScripts.
4. Keep editing the `.lua` files in the project folder. Rojo syncs filesystem changes **into** Studio. Save the Studio place with **File → Save to Roblox** or **File → Save to File** after connecting.
5. Press **Play** in Studio. Check **View → Output** for startup errors. Test two players with **Test → Start** / the local server tools to confirm each gets a separate lane.

## Build a place file (alternative to live sync)

With Rojo installed, run `rojo build default.project.json -o rift-run.rbxlx` in the project folder. Open `rift-run.rbxlx` in Studio. This creates a place file from the mapped source; use live sync for iterative changes. Rojo handles Luau and supported model files well, while terrain, CSG, and some Studio-only/binary properties should be authored in Studio and saved with the place.

## First run and persistence

1. Add the ProfileStore module before starting the server (see step 5 above).
2. Publish the development experience. In **File → Game Settings/Experience Settings → Security**, enable **Enable Studio Access to API Services** only for this separate test experience.
3. Start a local server with two players. Complete an enemy, leave, rejoin, and check that Essence/XP persist. Check Output for profile-load errors.
4. Disable/reset test data only through a deliberate test-data workflow. Do not enable Studio API access on the production experience while testing.
5. When ready, publish the reviewed place to the intended experience through Studio. Keep the Rojo project and Studio-authored assets backed up in version control.

## Common issues

- **Rojo command not found:** install Rojo CLI and reopen the terminal so PATH refreshes.
- **Studio cannot connect:** keep `rojo serve` running; check firewall/local connection settings and ensure the Studio plugin is enabled.
- **Missing ProfileStore:** ensure the module is named exactly `ProfileStore` and lives under `ServerScriptService.Packages` in the synced tree.
- **No save in Studio:** publish the test place and enable API Services for that test experience only.
- **Editing scripts in Studio appears to revert:** the filesystem is the source of truth for mapped scripts. Edit those files locally, or export Studio-authored code before mapping it.

## Viewing the blockout

The hub is currently generated by the server at runtime. In Studio edit mode, the camera shows only whatever is saved into the place, so this runtime-generated blockout appears after you press **Play**. To inspect the layout, press **Play** and use the normal Studio test camera controls; to orbit while not playing, author/save the scene as Studio geometry or later replace the blockout with exported .rbxm assets. The six base pads are arranged around the plaza; the portal corridor has Grasslands Easy, Normal, and Hard doors. The service kiosks are visual placeholders with ProximityPrompts, ready to connect to their systems.
